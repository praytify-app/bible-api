# Praytify Bible Gap Evaluation — 2026-07-10

## Executive Summary

The platform is architecturally sound and further along than it looks: 1,273 translations (14.5M verses, 1,019 languages) sit in the deployment artifact, the engine exposes a complete REST surface with live public docs, and the developer portal's key-management journey is code-complete. But production is silently broken: the gateway cannot reach its database, so sign-in, key creation, key validation, and usage tracking are all down, and the health check reports "ok" while it happens. Independent of the outage, there is no surface where a non-developer can read scripture, the dashboard's usage and profile APIs are stubs, poetry verses are truncated in the seeded data, and real OAuth secrets are committed to git. The next sprint should restore production, open a public reading path, and make the data trustworthy.

## Dimension 1: Bible data completeness & quality

### Shipped (wired end-to-end)
- **1,273 versions, 14,539,799 verses, 1,019 languages in the deployment artifact** (`bible-data.sql.gz`, verified by counting every `COPY` block row; 1,169 copyrighted-redistributable + 104 public domain). All have `verse_count > 0`, so none are hidden by the phantom filter (`open-bible-api/src/routes/versions.ts:163`).
- All seeding-spec items landed: license filter accepts redistributable entries (`open-bible-api/src/seeder/catalog.ts:73,277`), columns widened (`src/db/schema.ts:29`), transaction-per-version with 500-row chunks (`src/seeder/bulk-insert.ts:117,174-175`), resume support (`src/seeder/batch-runner.ts:187`). Final run: 1,169 imported / 112 skipped / 4 failed of 1,285 (`.cache/seed-progress.json`).

### Partial (needs finishing)
- **Poetry verse text is silently truncated in the seeded data.** The USFM parser captures text only on `\v` lines and drops `\q`/`\p` continuation lines (`open-bible-api/src/seeder/usfm-parser.ts:57-74`). Reproduced by running the actual parser on cached ASV: Psalm 23:2 loses "He leadeth me beside still waters." This affects every poetry line (Psalms, Proverbs, Job, most prophets) across all USFM-sourced translations — the full 14.5M-verse corpus carries this loss. Fixing it requires a parser fix plus re-seed and re-export.
- **Whether production serves 1,273 versions is unverifiable today.** The gateway requires an API key for `/v1/versions` and its DB connection is down; docs copy still says "600+ translations" (`open-bible-api/src/index.ts:57`). Prod may hold this artifact, an older one, or a partial set.
- **The deployment artifact carries no search infrastructure.** Zero `CREATE INDEX` / `CREATE EXTENSION` statements and no `search_vector` column in the dump (verified by full-stream grep). Search indexes exist only if `migrate.ts` was separately run against prod — unverified.
- **Globally-unique abbreviation constraint** (`open-bible-api/src/db/schema.ts:29`) collides distinct same-abbreviation translations across languages; contributor to the 112 skips.

### Missing entirely
- **`daily_verses` has 0 rows in the artifact** (verified count). The seeder is complete (`open-bible-api/src/seeder/daily-verses-seed.ts`, 366 curated verses) but was never run before export, so `/api/v1/daily` 404s every day (`open-bible-api/src/routes/daily.ts:55-62`).
- No retry or failure log for the 4 failed translations beyond the aggregate count.

## Dimension 2: Engine API surface & structured reading format

### Shipped
- Full REST surface, OpenAPI-registered and publicly documented: languages, versions (pagination + language/search/hasAudio filters), books, chapters, verses by chapter, reference lookup with ranges and parallel versions (`open-bible-api/src/routes/verses.ts:19,80-210`), full-text search, daily verse, admin routes, full-Bible download, ESV audio proxy. Scalar docs live at `api.praytify.bible/docs` (probed 200).
- Read-time text cleaning strips Strong's residue (`open-bible-api/src/lib/text-cleaner.ts:10-17`); pagination defaults 20/max 100; engine-level IP rate limiting.

### Partial
- **"Reader-ready" format is flat verse arrays only.** The parser discards paragraphs, poetry indentation, section headings, footnotes, and Psalm superscriptions (`usfm-parser.ts:73`). The schema stores number + text only (`schema.ts:72-83`). A client can render an ordered verse list, not a formatted reading view.
- **Search cannot use an index on its primary path** — `to_tsvector` computed per row at query time (`open-bible-api/src/routes/search.ts:131-152`); the stored `search_vector` column is never referenced; trigram fallback errors if `pg_trgm` is absent (see Dimension 1).
- **Cache headers imported in 6 route files, applied in zero** (grep-confirmed; only `daily.ts:87,101` sets them manually). README's "cache-friendly responses" claim is unmet.
- Two versioning identities for one service: API self-reports 1.0.0, images tagged 1.3.1, and compose files reference two different image names for the same code.

### Missing entirely
- No passage endpoint returning headings/paragraph structure; no red-letter, footnote, or cross-reference data anywhere in schema or parser.

- **Terms of Service / Privacy Policy** — LoginPage references both (`LoginPage.tsx:79`); no such routes exist (`portal/src/router.tsx:87-99` is the full tree).

## Dimension 6: Deployment, operations & security

### Shipped
- Multi-stage non-root Dockerfile; pinned tags for gateway/engine; healthchecks with `depends_on: service_healthy`; engine correctly internal-only; Postgres volume persistence (`docker-compose.prod.yml`); working manual build/push script (`scripts/deploy.sh`).

### Partial
- **P0: production gateway cannot reach Postgres.** Externally confirmed twice: `/health` reports `database: "disconnected"`, and a fake-key probe returns "API key validation failed" — the DB-error catch branch (`src/middleware/api-key.ts:74-80`), not the "invalid key" branch. Root cause is config-level in Dokploy: either `DATABASE_URL` is unset (client constructor throws on import, `src/db/client.ts:7-9`) or points at the wrong host (must be `postgres:5432`; the service exposes no host ports). Cannot be distinguished or fixed from this machine.
- **Health masks failure**: `/health` returns HTTP 200 "ok" with the DB down (`src/index.ts:47-52`); the compose healthcheck tests HTTP-ok only (`docker-compose.prod.yml:38`), so Dokploy shows green during a total platform outage.
- **Migrations never run in prod**: image CMD is `node dist/index.js` with no migrate step (`Dockerfile:38`); the untracked `scripts/run-migration.sql` is a hand-rewritten replay of `drizzle/0000_overrated_vision.sql` — evidence of manual schema surgery with no repeatable path.
- **Portal image drift**: pinned to `:latest` while siblings are version-pinned (`docker-compose.prod.yml:87`); a stale pull can silently mix versions.
- **Data deployment is destructive scp-and-restore** (`--clean --if-exists` DROP TABLEs, `scripts/export-bible-data.sh`) with no evidence the complete 1,273-version artifact was ever imported to prod.

### Missing entirely
- **Committed OAuth secrets (rotate now)**: `.env.production` is git-tracked with real GitHub + Google client secrets (lines 15-20), in history since commit `4d9882b`. Treat as compromised.
- **CI/CD** — no `.github/` or any CI config (verified).
- **Observability** — zero matches for any metrics/logging/error-tracking library across `src/` and `package.json`; 8 `console.error` call sites total. No alerting or uptime monitoring — consistent with the outage going unnoticed.
- **Staging environment.**

## Goal Statement (copy-paste ready)

> **Sprint Goal: Restore the platform and open the Bible to everyone.**
>
> When this sprint lands, a developer can sign up at praytify.bible, mint a `pb_` key, make a successful API call, and watch real usage appear on their dashboard; any visitor, with no account, can browse all 1,200+ translations and read any chapter in a clean, structured reading view; and the scripture text we serve is complete, including every poetry line we currently truncate.
>
> The work: fix the Dokploy `DATABASE_URL` so the gateway reaches Postgres, add a migrate-on-boot step, and verify OAuth envs are set (or enable email/password auth as a fallback sign-up path). Rotate the GitHub/Google OAuth credentials committed in `.env.production` and untrack the file. Make catalog endpoints (`/v1/versions`, `/v1/languages`) publicly readable, fix the portal's broken translations browser, and build a `/read` route in the portal (version → book → chapter navigation on the engine's chapter endpoint). Implement the stubbed `GET /api/dashboard/usage`, `/summary`, and profile routes against `usage_daily` and `developer_profiles`. Fix the USFM parser to capture `\q`/`\p` continuation lines, re-seed, run the daily-verses seeder, and ship a new data artifact with search indexes included.
>
> Cross-cutting: every public claim must match deployed reality (drop "Global CDN," "99.9% uptime," and "Unlimited requests" until true; make the translation count live from the API), `/health` must report degraded status when the DB is down, and CI must run the test suite on every push.
>
> **Definition of done:** (1) `curl https://api.praytify.bible/health` shows `database: "connected"` and an unauthenticated `GET /v1/versions` returns 1,200+ versions; (2) a fresh user completes sign-up → key creation → a 200 API response → non-zero "Requests Today" on the dashboard; (3) `GET /v1/verses?ref=Psalm 23:2&version=ASV` returns both poetry lines and `/v1/daily` returns a verse; (4) an anonymous visitor reads John 3 at praytify.bible/read without logging in.
