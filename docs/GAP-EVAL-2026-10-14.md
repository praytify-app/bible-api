# Praytify Bible Gap Evaluation: 2026-10-14

## Executive Summary

The corpus and the core read path are solid: 1,288 translations are live, the public reader works, and the July outage fixes held. What stands between this and a platform other people can adopt is the layer around the data. The published API docs are broken in production, a fresh clone cannot run its migrations, there is no license, README, CI, SDK, or browser-safe key, and nothing is cached or compressed, so every read of an immutable chapter costs a database round trip. Security has three High findings: a reachable hono CORS ReDoS, quota bypass by minting more keys, and (in the Praytify app, not this repo) a web proxy that hands the master key to any caller who sets one request header. Praytify itself can only partly use the platform today: its offline download is broken by a contract mismatch, and all of its server traffic shares a single 1,000-requests-per-hour fuse in the engine.

## Dimension 1: Security

### Shipped
- No path escape through the proxy: paths are normalized before routing and the target host is fixed (`src/middleware/proxy.ts:13-16`). Verified locally with the locked hono and node-server versions.
- Engine admin routes are unreachable through the gateway: `Authorization` is never forwarded (`proxy.ts:20-31`) and the engine has no public port (`docker-compose.prod.yml:47-66`).
- No SQL injection found: every query binds input as parameters; no `sql.raw`.
- Only placeholder env files are tracked today. Gateway and engine images run as non-root.
- **Corrected in the third pass:** the July history purge is incomplete. It removed `.env.production`, but production credentials were also committed inline in `docker-compose.prod.yml` and remain in main's history. See "Third pass" below.

### Partial
- Input validation: engine search accepts negative and unbounded `limit`/`offset` (`open-bible-api/src/routes/search.ts:73-74`); `ILIKE` does not escape `%` or `_` (`:172`), so `q=%` scans everything; key names are uncapped (`src/routes/keys.ts:46`); a malformed revoke id returns 500 (`keys.ts:78-84`).
- Containers: no `read_only`, `cap_drop`, `no-new-privileges`, or resource limits; the portal runs nginx as root on floating tags (`portal/Dockerfile:2,18`).
- Error detail leaks: the auth handler returns `details: String(err)` (`src/index.ts:100`).

### Missing
- Security headers on both domains (live check): no CSP, HSTS, `frame-ancestors`, or `nosniff`; the dashboard can be framed.
- Request body limits (`proxy.ts:43-45` reads any body fully into memory), upstream timeouts (`proxy.ts:48`), and a Postgres `statement_timeout`.
- Least-privilege database roles: gateway and engine share one superuser `DATABASE_URL` (`docker-compose.prod.yml:21,53,72`).
- Patched dependencies: hono 4.12.8 carries a reachable CORS ReDoS (fixed in 4.12.34; 462 ms per crafted preflight measured locally); better-auth 1.5.5 carries an OAuth account-linking advisory (fixed in 1.6.11); drizzle-orm 0.45.1 an identifier SQL injection advisory (fixed in 0.45.2). All fixes sit inside the existing `^` ranges.

### Cross-cutting concerns
- **Praytify app, High:** `../praytify/apps/web/app/api/bible/[...path]/route.ts:40-71,149-156` attaches `MASTER_API_KEY` to any `/v1` path, gated only by `Origin`, `Referer`, or `Sec-Fetch-Site`, all client-controlled. Any script gets unmetered search and download and can exhaust the engine budget that real users share. Read from code, not exercised live; whether that route is deployed is unverified.

## Dimension 2: Authentication and authorization

### Shipped
- GitHub and Google OAuth via BetterAuth with database-stored OAuth state and trusted origins (`src/auth/index.ts:6-47`).
- Every dashboard handler validates the session and scopes queries by `user_id` (`src/lib/session.ts:11-19`).
- Keys: 192-bit random, stored as SHA-256 with a unique index (`src/db/schema.ts:107`), shown once, revocable, `last_used_at` recorded.

### Partial
- Rate limiting lives in process memory in all three layers (gateway `src/middleware/rate-limit.ts:27`, engine `rate-limit.ts:15`, BetterAuth): counters reset on deploy and multiply with replicas. The engine's map never evicts, and compose sets `RATE_LIMIT` while the code reads `RATE_LIMIT_MAX`.
- The master key is one static secret compared with `===` (`src/middleware/api-key.ts:48`), never rotated, logged as `master`, and still capped by the engine's per-IP 1,000/hour.
- Usage metering only rolls up "today" (`src/jobs/usage-aggregation.ts:16`), so requests in the last hour before UTC midnight are never counted.

### Missing
- **Quota bypass (High):** one account can mint unlimited keys (`keys.ts:41-71`), each with its own 1,000/day (`rate-limit.ts:135,154`).
- Tier enforcement: `developer_profiles.tier` (`schema.ts:179`) is display-only.
- Key lifecycle: no kinds, scopes, origins, expiry, or rotation; no browser-safe key, while the quickstart shows a secret key inside a browser `fetch` (`portal/src/pages/QuickStartPage.tsx:60-61`).
- Operator tooling and a security audit log.

## Dimension 6: Performance and scalability

### Shipped
- The proxy streams responses and reuses connections; usage logging never blocks a response; the engine indexes every chapter and verse lookup and serves search from GIN indexes.

### Partial
- Three database round trips per keyed request: key lookup (`api-key.ts:59`), a `last_used_at` write on every request (`:76`), and a log insert. None cached.
- The hourly rollup filters on `DATE(created_at)` (`usage-aggregation.ts:16`), defeating the index and scanning up to 90 days of logs.
- Reading one chapter costs four engine queries (`open-bible-api/src/routes/chapters.ts:92-145`).

### Missing
- **No HTTP caching or compression anywhere** (live): no `Cache-Control`, no `ETag`, no gzip. The engine's `cacheControl` helper is imported in six routers and called in none (`open-bible-api/src/middleware/cache.ts:3`). Psalm 119 ships as 28 KB uncompressed. The proxy forwards only four headers, so `If-None-Match` and `Accept-Encoding` never reach the engine (`proxy.ts:20-25`).
- Download runs about 1,256 sequential queries and builds the result in memory (`versions.ts:376-405`); parallel `?ref=` has no cap on version count (`verses.ts:102`).
- Horizontal scale blockers: in-memory limiters, scheduled jobs running in every replica, no graceful shutdown, default pools of 10.
- Portal: one 741,753-byte bundle (219,722 gzipped), no route splitting (`portal/src/router.tsx:7-18`), recharts on every public page, render-blocking Google Fonts (`portal/index.html:9-11`), and nginx serving it uncompressed.

## Goal Statement (copy-paste ready)

> **Sprint Goal: Open the platform.**
>
> When this sprint lands, a developer can clone the repo, run one command, and have the full stack with sample translations on their machine; can read accurate API docs at api.praytify.bible/docs; can drop `<praytify-verse reference="John 3:16">` into any web page with no key; and can mint a publishable key locked to their site's origin or a secret key for their server, each with a real quota. Praytify reads, searches, and downloads through a revocable internal key instead of a shared master secret, and its offline download works again.
>
> The work: upgrade every package across gateway, portal, and engine, starting with the hono, better-auth, and drizzle security fixes; fix the OpenAPI paths and Scalar URL; give the gateway its own migrations table with a baseline for production and migrate on boot under an advisory lock; add key kinds, origins, tiers, expiry, and rolling, with per-user quotas in a pluggable Redis or memory store; cache key lookups, batch usage logs, fix the midnight rollup, and add `ETag`, `Cache-Control`, compression, and an LRU read cache; bound and de-N+1 the download, search, and parallel endpoints; make `?ref=` public and return `bookCode` and `chapter`; make the daily verse honour `version`; ship the TypeScript SDK and the embed widget; and rebuild the portal on the Core 2 structure with the Sacred Dawn brand, mobile navigation, dark mode, a reader with verse sharing, a key manager, and an embed builder.
>
> Cross-cutting: security headers, body limits, timeouts, and constant-time comparisons on every service; every claim on the site traceable to code or data; WCAG AA in both themes; CI running typecheck, lint, and tests on every push; LICENSE, README, CONTRIBUTING, and SECURITY in place; and the Praytify proxy fix documented and handed to the Praytify owner, since that repo is outside this sprint's write scope.
>
> **Definition of done:** (1) `curl -sI https://api.praytify.bible/v1/chapters/WEB/JHN/3/verses` shows `ETag`, `Cache-Control`, and `content-encoding` after deploy, and `/docs` renders operations under `/v1`; (2) on a clean clone, `scripts/dev-stack.sh up` brings up Postgres, engine, and gateway with sample data, and the gateway and engine test suites plus the portal's Playwright and axe suites pass against it; (3) a publishable key is rejected from a non-allowlisted origin and accepted from an allowed one, and a 21st key per user is refused; (4) `pnpm audit --prod` reports zero critical and zero high advisories in all three packages.
